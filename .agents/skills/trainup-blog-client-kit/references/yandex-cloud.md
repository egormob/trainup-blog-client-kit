# Yandex Cloud: настройка и публикация

Этот путь предназначен для прямой схемы «файлы на компьютере → сборка → Yandex
Object Storage». GitHub не нужен для работы сайта. Используй этот маршрут только когда клиент выбрал такой хостинг. Система согласий не использует БД, YDB, Functions или ресурсы автора; ради добавления согласий на существующую страницу облачные аккаунты не создаются.

## Границы участия владельца

Владелец сам выполняет только вход, MFA, принятие условий и подключение оплаты.
Показывай одно действие за раз, после чего проверяй результат. До создания
платного ресурса назови актуальную цену или открой официальную страницу тарифа и
дождись явного согласия.

Секреты принимает только терминал со скрытым вводом или штатное хранилище. Не
передавай секреты аргументом команды, не записывай в `.env`, статью, отчёт или
историю версий. После проверки сообщай `Ключ сохранён` или `Вход выполнен`.

## Минимальная схема

Используй актуальные команды из официальной документации:

- [Yandex Cloud CLI для Object Storage](https://yandex.cloud/en/docs/storage/tools/yc-cli)
- [настройка статического сайта](https://yandex.cloud/en/docs/storage/operations/hosting/setup)
- [роли Object Storage](https://yandex.cloud/en/docs/storage/security/)

Не передавай владельцу сразу весь список ниже. Выполняй сам и останавливайся лишь
на ближайшем человеческом действии.

### 1. Вход владельца

Если `yc` отсутствует, предложи официальный установщик для текущей системы.
Перед запуском скачанного скрипта объясни, что он меняет файлы программы и `PATH`,
и предложи более безопасную ручную загрузку архива с той же официальной страницы.
Затем запусти:

```text
yc init
```

Владелец сам входит в Яндекс, проходит MFA, принимает условия и при необходимости
подключает оплату. Не запускай видимый браузер без предупреждения. Не используй
`yc config list` и другие команды, способные показать учётные данные.

### 2. Отдельная область блога

Под активным входом владельца создай отдельную папку Yandex Cloud только для
блога. Все значения сначала получи сам и подставь в готовые команды: не оставляй
в копируемом блоке `<скобки>` или места, которые пользователь должен редактировать.

Для первого бакета выбери глобально уникальное имя из строчных латинских букв,
цифр и дефисов, без точки. Это даст рабочий технический HTTPS-адрес. Установи
разумный предел размера, по умолчанию 1 ГиБ, и до создания напомни, что хранение
и запросы Object Storage могут тарифицироваться. Создай публичное чтение объектов
и их списка, затем включи статический сайт с `index.html` как главной страницей.

Настройки сайта запиши во временный JSON внутри `.blog-state/yandex`, а не в
отслеживаемые файлы. Для включения сайта используй штатную команду:

```text
yc storage bucket update --name ИМЯ_БАКЕТА --website-settings-from-file ПУТЬ_К_НАСТРОЙКАМ
```

Эту строку владельцу не показывай с заглушками: агент обязан подставить точные
безопасные значения и выполнить её сам после подтверждения облачной записи.

### 3. Техническая учётная запись

Пока активен вход владельца, создай отдельную техническую учётную запись издателя.
Дай ей роль `storage.editor` только в специально созданной папке блога. Эта роль
нужна для чтения, загрузки, замены и ограниченного отката объектов; она не даёт
права менять публичный доступ. Не выдавай общие роли `editor` или `admin` на всё
облако. Публичный доступ к бакету настраивает владелец на предыдущем шаге.

Создай авторизованный ключ сразу в системной папке настроек вне проекта:

- macOS: внутри `Library/Application Support/TrainUpBlogKit` текущего пользователя;
- Windows: внутри `AppData/Roaming/TrainUpBlogKit` текущего пользователя.

Команда создания ключа должна писать JSON прямо в этот файл и никогда не печатать
его содержимое. На macOS оставь доступ к файлу только текущему пользователю; на
Windows ограничь права штатным ACL. Затем создай отдельный профиль `yc`, укажи в
нём этот файл и ID папки блога. Не активируй профиль глобально: команды кита
получают его явным параметром `--profile`.

Проверь новым профилем чтение настроек точного бакета. Только после успешной
проверки сообщи:

```text
Ключ сохранён
```

### 4. Первый и последующие выпуски

Сначала выполни:

```text
node scripts/blog-kit.mjs build
node scripts/blog-kit.mjs verify
node scripts/blog-kit.mjs publish-plan --bucket ИМЯ_БАКЕТА --profile ИМЯ_ПРОФИЛЯ
```

Перед показом подставь точные значения. `publish-plan` ничего не меняет в облаке:
он показывает бакет, все ключи объектов, MIME/cache-настройки, объём и контрольный
код. Напомни о возможной тарификации и попроси подтвердить именно этот код.

После подтверждения выполни:

```text
node scripts/blog-kit.mjs publish --bucket ИМЯ_БАКЕТА --profile ИМЯ_ПРОФИЛЯ --confirm-hash КОНТРОЛЬНЫЙ_КОД
```

Кит сначала сохраняет только прежние версии целевых объектов, загружает ассеты,
затем HTML и GEO-файлы, перечитывает каждую загрузку и пишет локальный отчёт.
Технический адрес бакета без точки имеет вид
`https://ИМЯ_БАКЕТА.website.yandexcloud.net/`.

Для отката покажи владельцу точную версию и её контрольный код, а затем используй:

```text
node scripts/blog-kit.mjs rollback --release ВЕРСИЯ --profile ИМЯ_ПРОФИЛЯ --confirm-hash КОНТРОЛЬНЫЙ_КОД
```

Откат затрагивает только карту объектов выбранного выпуска. Никогда не затрагивай
чужой бакет или исходные адреса статей TrainUp.
