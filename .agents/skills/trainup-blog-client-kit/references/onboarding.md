# Первый запуск без технических знаний

## Стиль сопровождения

Давай владельцу одно простое действие за раз. Не выдавай сразу длинную стену
команд или целый экран настроек. После каждого шага дождись понятного результата,
объясни его обычными словами и только потом переходи дальше.

Для каждой команды кратко скажи:

1. что она сделает;
2. зачем она нужна сейчас;
3. что может пойти не так;
4. есть ли более безопасный ручной вариант.

Команду показывай отдельным блоком, готовым для копирования без редактирования.
Не смешивай команду и секрет в одной строке.

## Начальные вопросы

Сначала спроси дословно:

> Где хранить исходники и историю блога?
>
> а) Только на этом компьютере — проще, быстрее и экономнее по токенам (рекомендуется).
>
> б) Локально на компе + Гитхаб — удалённая копия и совместная работа; потребуется дополнительный аккаунт и более длинная настройка. Выбирайте, если точно понимаете, зачем это нужно.

Историю версий на компьютере создавай в обоих вариантах. Если выбран первый,
больше не поднимай тему GitHub. Если выбран второй, проверь своё подключение к
GitHub и предложи подключить управление, когда его нет. Не показывай отдельную
инструкцию: человек, выбравший этот путь, получает обычную поддержку Codex.

Затем спроси название блога и предложи новую отдельную папку. Никогда не выбирай
корень диска, домашнюю папку целиком или папку с другим проектом. Если папка уже
содержит файлы, сначала покажи их и предложи другое место.

## Терминал и секреты

Если владельцу нужно открыть терминал в приложении Codex, скажи: «Нажмите в
правом верхнем углу значок терминала `>_` — прямоугольник, который может
напоминать маленькую духовку». Если интерфейс выглядит иначе, попроси открыть
встроенный раздел «Терминал» и не заставляй человека угадывать.

Пароль, ключ, токен и код подтверждения никогда не запрашивай в чат или обычное
сообщение. Сначала дай отдельную команду, которая запускает скрытый ввод или
штатное хранилище учётных данных. Затем попроси вставить значение именно туда.
Введённый секрет не должен отображаться, попадать в историю команд, `.env`,
настройки статьи или файлы, отслеживаемые историей версий.

После реальной проверки выводи однозначный результат:

```text
Ключ сохранён
```

или:

```text
Вход выполнен
```

Не сообщай об успехе, пока проверка не прошла. MFA, принятие условий, подключение
оплаты и покупку нельзя обещать выполнить без владельца.

## Порядок первого выпуска

1. Скачай публичный кит без авторизации GitHub.
2. Проверь macOS или Windows, Node.js и историю версий. Yandex Cloud CLI нужен только при выборе этого хостинга.
3. Создай папку блога командой `node scripts/blog-kit.mjs init`.
4. Выясни, есть ли хостинг. Для нового Cloud-хостинга настрой Yandex Cloud; для работающей страницы сохрани её хостинг. Для согласий БД не нужна.
5. Спроси: «Какую статью вы хотите, чтобы я создал? Дайте текст и необходимые
   материалы».
6. Последовательно запроси реквизиты, UTM, решение по GEO и собственные параметры согласий по consent-installation.md.
7. Собери и проверь статью на разных ширинах экрана.
8. Покажи точный план публикации и предупреждение о возможной стоимости.
9. Выполни согласованный план публикации. Для нового Cloud-хостинга сначала проверь технический домен. Для существующей страницы публикуй только разрешённые изменения.
10. Зафиксируй точку возврата и предложи собственный домен.
