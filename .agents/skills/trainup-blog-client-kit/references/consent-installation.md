# Установка согласий — клиентский комплект 1.1.1

Применяй по заголовкам PDF/guide.md «Создать новый лендинг с согласиями» и «Добавить согласия на существующий лендинг». Перед первым действием прочитай `docs/guide.md` полностью: описание работы, ограничения доставки, хранения, отзыва и удаления входят в обязательный контракт. Не обещай облачный журнал, автоматическое удаление у Яндекса или абсолютную доставку. Consent-runtime версии 1.2.0 находится в `kit/consent`; Node-адаптер — `scripts/consent-kit.mjs`, SHA — `kit/consent/manifest.json`. Python, Git-тег исходной страницы и приватный Landings для сборки не нужны.

## Создать новый лендинг с согласиями

1. Скачай публичный ZIP версии v1.1.1 из указанного владельцем репозитория. Проверь структуру, прочитай корневой AGENTS.md и этот навык. Прочитай onboarding.md, проверь среду doctor; веди владельца по одному действию. Новая установка использует отдельную папку, сохраняет историю и не затирает прежний проект.
2. Выбери basic, advanced или consent. Получи собственные материалы и данные оператора. Первые два дизайна сохраняются как демонстрационные образцы автора; замени их содержание, бренд, изображения и все целевые ссылки под клиента. В третьем примере нет активного счётчика и контактов автора.
3. Заполни `blog/site.json`: `siteName`, `baseUrl`, автора, footer, GEO и полный объект `consent` по `kit/consent/settings.example.json`. Номер счётчика: собственный или 0. Явно согласуй `newsletterEnabled` и `serviceIdsEnabled`, фактические сборщики, версию, цели и документы. Параметры конкретной статьи можно хранить в `article.json.consent`; slug сборка задаёт равным article.id. Изменение реальной обработки требует новой версии согласия и обновления документов. Секретов в JSON быть не должно.
4. Если документов нет, собери фактические цели, данные, сроки, получателей и порядок обращений; подготовь тексты на данных клиента, согласуй с ним и размести действующие документы. Не копируй документы исходного оператора. Не ставь вместо документа ссылку на генератор GetCourse; без реальной рассылки оставь её флаг false. Не описывай отсутствующий сбор/сервер как активный.
5. Создай статью штатным CLI `node scripts/blog-kit.mjs create-article --slug ИМЯ --template consent`, подставив точные значения сам. В content.html оставь единственный `<!-- LANDING_CONSENT -->` в контейнере ширины CTA и штатный слот footer. Пометь действия `data-consent-cta="signup"` либо `data-channel`; внешняя ссылка нативная `target="_blank" rel="noopener"`. Сохрани SEO/GEO и безопасный UTM-router. При использовании прежних штатных образцов builder добавляет компонент над первой CTA автоматически; для своего дизайна подготовь маркер адресно. Сравни ширину и выравнивание.
6. Выполни `node scripts/blog-kit.mjs build`, `node scripts/blog-kit.mjs verify`, `node --test`, `node scripts/verify-package.mjs`. В новых проектах site.consent включён по умолчанию, все три шаблона получают один компонент. Для старого проекта отсутствие site.consent сохраняет прежнее поведение: его нельзя считать уже мигрированным. Проверь браузер и документы по checklist ниже.
7. Для нового хостинга используй yandex-cloud.md; база YDB и серверная доставка не создаются. Если хостинг есть, сохрани его. Разрешения/стоимость/публикация проходят штатный review точных файлов, snapshot и readback. После публикации сохрани версию, адрес, настройки и результаты в проекте клиента.

## Добавить согласия на существующий лендинг

1. Получи явный URL и исходники или разрешённый доступ к конкретной странице. Сохрани исходник и точку возврата. Не создавай новый проект или Cloud вместо существующего. Для старого клиента кита обновляй только проверенные файлы кита, не трогая blog, .blog-state, ключи, site.json и изменённые пользователем исходники. Покажи конкретные изменения и не заменяй пользовательский файл молча.
2. Изучи фактические сборщики в HTML, внешних скриптах, менеджере тегов, CMS, формах и iframe. Удали/отключи старый автономный loader Метрики, его noscript-пиксель и обработчики целей вне нового runtime. Остальные необязательные сборщики подключи к соответствующему согласию отдельно либо сообщи конкретный незакрытый доступ. Автоматический поиск адаптера — только дополнительный предохранитель, а не полный аудит CMS.
3. Если компонент уже есть, определи версию и выполненные изменения. Не вставляй второй. Для обновления восстанови известные точки вставки из сохранённого исходника или адресно замени только ранее вставленный компонент; перепроверь старый код и конфигурацию.
4. В отдельной рабочей копии HTML поставь ровно один `<!-- LANDING_CONSENT -->` перед основной CTA в её контейнере, вне form/label; ровно один `<!-- LANDING_LEGAL_FOOTER -->` в существующем footer. Добавь data-consent-cta/data-channel нужным действиям. Внешние ссылки — target=_blank rel=noopener. Формы, платежи и отправку лидов проверяй отдельно: один data-атрибут на кнопке не блокирует программную отправку формы.
5. Подготовь явный JSON клиента. Запусти `node scripts/consent-kit.mjs build --settings ФАЙЛ --page РАБОЧИЙ_HTML --output НОВЫЙ_КАТАЛОГ`; затем `node scripts/consent-kit.mjs verify --output НОВЫЙ_КАТАЛОГ`. Подставь точные пути и выполни команды сам. Builder отказывается перезаписывать каталог, валидирует параметры, оба маркера, ранний tracker и контрольные суммы. HTML вне маркеров сохраняется побайтно, включая SEO/GEO/подстановки. Подготовительные правки страницы остаются отдельным diff.
6. Для CMS можно получить inline div и юридический блок: та же команда с `--component-only` вместо `--page`. Файлы consent-component.html и legal-footer.html вставляет сам агент в разрешённую область. Для GetCourse нужно проверить нижние/native сборщики и формы; переносимая вставка не удостоверяет согласие всей платформы. Сохрани принятые юридические ссылки клиента и не затрагивай другие страницы.
7. Проведи checklist, сравнение дизайна/форм/UTM/SEO и адресную публикацию с откатом. Установка в новый каталог сама по себе ничего не публикует.

## Настройки и счётчик

Обязательные поля компонента: slug, counterId, newsletterEnabled, serviceIdsEnabled, consentVersion, buttonGoal, readyGoal, policyUrl, consentUrl, offerUrl, advertisingConsentUrl, brandName, brandUrl, operatorRequisites, contactTelegramUrl, phone, phoneDisplay, email. Полный starter дополнительно требует pageUrl, telegramUrl, vkUrl, title, description, intro, lead, benefits, heroAlt. URL — HTTPS без credentials, телефон международный. Не оставляй example.invalid, нулевые реквизиты и демонстрационные контакты в опубликованном сайте. Без рассылки её URL остаётся неактивным параметром и не выводится.

Для самостоятельного полного starter используй build без --page/--component-only. Для основной статьи предпочтительна штатная сборка blog-kit: она сохраняет общие SEO/GEO/UTM. Встроенный starter остаётся noindex до собственной редакционной приёмки.

Помоги владельцу войти в Метрику и создать/выбрать собственный счётчик. С его разрешением создай/проверь две JavaScript-цели: готовность страницы и клик. При отсутствии доступа веди по одному человеческому действию, не подменяй отчёт очередью SDK. Секреты и доступы — только штатным безопасным способом. Номер не создаёт ресурс и не доказывает доступ. CounterId=0 — валидный режим без SDK и пунктов аналитики; если клиент заказал аналитику, её реальная проверка остаётся обязательной.

## Обязательные проверки

- Исходные digests и выходные SHA; независимая установка без Python, Git/сети при сборке; собственная конфигурация и отсутствие старых endpoint/счётчиков/секретов. Runtime guard.js/cookie-consent.js/consent-analytics.js не переписывать.
- Чистый контекст: до выбора нет tag.js, noscript-пикселя и запросов необязательных сборщиков. Пусто блокирует CTA также до загрузки JS, по клавиатуре и средней кнопке.
- Полное/частичное согласие, сохранённый отказ со свободным переходом без SDK, черточка, «Принять все», повторное открытие, документы без включения чекбокса.
- Отзыв после запуска, очистка доступных _ym в cookie/localStorage и прекращение будущего сбора; новый документ восстанавливает отказ. Не заявлять удаление HttpOnly, чужого домена, прежних данных Яндекса или подписки бота. Проверь описанный оператором путь обращения и контакты.
- Истечение 180 дней, другая версия, повреждённое/будущее значение, смена проекта, недоступное хранилище, изменение во второй вкладке. Без сохранения выбор может действовать лишь в текущем визите.
- Холодный SDK и быстрый native переход: исходный документ жив, opener отсутствует, одна цель собственного проекта с нужным каналом. Отдельно прочитай реальную цель в отчёте своего счётчика. Заглушка и HTTP 200 не доказывают регистрацию. При отсутствии доступа пометь эту проверку как незавершённую; не объявляй настроенную аналитику проверенной.
- Mobile/tablet/desktop, фиксированные header/footer панели, скролл, ширина и выравнивание компонента с CTA, отсутствие переполнения. Для существующей страницы сравни формы, дизайн, ссылки, canonical, JSON-LD, индексацию и UTM до/после.
- Проверь фактические сервисы и юридические документы, версии, данные оператора, применимость рассылки/бота, публикацию/readback и откат. Сообщи фактические результаты и ограничения браузеров. Публикация не выполняется до закрытия необходимой проверки.
